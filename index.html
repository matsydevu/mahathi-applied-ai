STUDY 01 · RELIABILITYARCHITECTURE STUDY

An evaluation harness for enterprise agents

How do you know an agent is getting better without quietly making it less safe?

Design questions

What counts as task success? Which failures need deterministic tests? Where is model-graded evaluation useful, and where does it need human review?

What I'd implement

A versioned scenario set, repeatable runs, rubric-based scoring, tool-call validation, regression comparisons, and a review queue for ambiguous cases.

Trade-off to defend

Offline scores are a release signal, not proof of real-world quality. Pair them with production sampling, user feedback, and risk-weighted review.

STUDY 02 · TRUST & DATAPROPOSED REFERENCE ARCHITECTURE

A permission-aware knowledge assistant

A useful answer is not useful if it reveals information the person asking should never see.

Design questions

How are permissions inherited? How quickly do revoked permissions propagate? What happens when sources conflict or retrieval confidence is weak?

What I'd implement

Connector-based ingestion, document-level metadata, identity-aware retrieval filters, source citations, explicit abstention behavior, and access-control tests.

Trade-off to defend

Retrieval relevance and authorization are separate concerns. Enforce access before content reaches the model, then test for leakage across roles and tenants.

Design questions

Which tools are discoverable? How are scopes bound to a user and session? Which actions require confirmation, idempotency, or rollback?

What I'd implement

A typed tool registry, per-tool authorization, short-lived credentials, input validation, approval gates for consequential writes, and immutable audit events.

Trade-off to defend

More tools increase capability and attack surface. Start with narrow, composable tools and expose only the minimum capability needed for each workflow.

STUDY 04 · OPERATIONSARCHITECTURE STUDY

Observability and graceful failure for agents

When an agent goes off course, operators need to understand what happened and users need a safe next step.

Design questions

What should be logged without collecting sensitive content? Which errors are retryable? When should the system stop and ask a person?

What I'd implement

Correlated traces, latency and token-cost metrics, redacted logs, tool error taxonomy, escalation thresholds, and operator-facing replay of sanitized traces.

Trade-off to defend

Observability must not become indiscriminate data collection. Minimize sensitive payload retention while preserving enough context to debug behavior.
